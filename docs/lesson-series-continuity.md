# Start lesson history from an explicitly confirmed semester cohort

An unassigned card offers “この授業から次回・共有メモの連動を開始”. Its history page previews the observed occurrence and either a new student/class or an explicitly selected existing owner. Confirmation creates the owner (if new), an empty anchor record, its event link and the series boundary in one audited, idempotent D1 transaction. No old record, pending plan, name-keyed profile or Calendar description is copied or changed. A pending plan remains available for the existing explicit compare/adopt workflow.

A rule is scoped to the calendar, Google recurringEventId, verified parent created/iCalUID, expected parent/occurrence title and the anchor originalStartTime. Future matching occurrences use that fixed owner without weekly confirmation. Reads do not create records; the first explicit save creates one occurrence record with revision, owner, latest-boundary, exclusion and absent-link guards. Next-plan and normal record editing share the same guarded persistence. The default UI now previews the configured semester containing the selected occurrence. Actual scheduled events, including blank lessons, define numbering; the semester start and first actual lesson date are distinct.

The latest applicable boundary is selected before validating a title. A title that later returns to an older student's name never revives an older rule. Any explicit occurrence link, including a null detach tombstone, overrides series inference. Parent failure/recreation, changed titles and unconfirmed legacy records hold content instead of guessing. Original occurrence time defines the boundary: an older lesson moved later does not enter the new history. Foreign confirmed future records or conflicting future boundaries prevent automatic start and require an explicit ownership/range decision. No existing owner links are bulk reassigned.

The semester preview collects same-title candidates within the same selected calendar and displays every candidate and hold before confirmation. Distinct verified recurring parents can be confirmed together for one fixed owner. Other owners, explicit detach, exclusions and unknown legacy rows remain held. The transaction creates one owner and one anchor per confirmed parent, not a record for every blank occurrence. Single events require the existing explicit individual binding workflow. Single events have no authoritative series identity: use the existing individual binding workflow and next-candidate confirmation. They cannot silently authorize unrelated same-name events. Explicitly created owner records and series records use fixed-owner shared memos. Existing name-keyed student profiles stay intact; they are not automatically imported. Saving a fixed-owner memo makes it available to that owner's records.

Shared memos have their own revision and audited UUID. Every card verifies its exact observed target and owner before displaying the memo; the history page intentionally accesses the explicitly selected fixed owner without requiring a surviving schedule. Input and operation IDs survive reload, and another tab's successful save cannot clear this tab's recovery copy. Other-tab copies are explicit recovery material, not automatic input adoption. Late reads cannot replace newer saved state. A 409 requires comparison and explicit edit resumption; an unknown outcome permits audit/readback only, never automatic resend. The same unknown-outcome recovery covers the first plan or confirmation-test/homework/lesson-memo/completed save.

## Rollout prerequisites

Local implementation only. Apply additive `worker/migrations/lesson-series-continuity.sql` before the new code/UI; no production change or public PR is performed by development. Existing tables, original records, exclusions and Calendar text must remain unchanged. The normal bootstrap includes these two tables for isolated fixtures. Missing parent metadata or missing migration is not authorization to relax a guard. Read-only verification uses synthetic fixtures and restored copies; actual class ownership is not established during tests.

## Semester list and count

`/semester/preview` is read-only and uses the real `terms.label/start_date/end_date`, current Google expanded events, owner links, legacy records and exclusions. `/semester/start` replays the same fresh preview and commits all selected parent anchors in one audited UUID transaction. Name matching proposes candidates only; confirmed ownership remains ID based. No old contents or pending drafts are copied. A conflicting future owner/boundary blocks the affected series instead of silently overriding it.

`/semester/schedules` projects actual events for the selected fixed owner, including virtual blank occurrences. Deleted/cancelled/excluded/unverified instances do not count. It performs no D1 writes. The history page retains all saved records separately so deleted schedules and earlier history remain accessible. Counts on Tutor/Home use the same owner projection and exact current event observation. Reads are bounded to two concurrent owners and do not block the initial daily cards; failed or stale reads show an unknown count instead of reverting to name-only counts. Unassigned cards label same-name counts as unconfirmed candidates.

Synthetic regression: configured semester starts 2026-09-03, first occurrence 09-08, 11-03 is planned lesson 9/11, all 11 blank occurrences appear in history with only one anchor record persisted. This is a scheduled ordinal, not a completed-lesson count. Production class anchors remain unset pending the explicit rollout stage.
