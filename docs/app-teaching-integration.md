# Teaching in the optional Works app

## Scope and safe boundaries

`/app/#!/teaching/` opens today's JST schedule. Civil-date routes and encoded calendar/event detail routes support direct links, reload, date navigation and native Back/Forward. Existing `/tutor/`, the original home and all original APIs remain. There is no DB/schema/API migration.

The day list is a schedule list; it does not claim that an unselected record is empty, incomplete or ownership-verified. Detailed records are read through the existing `GET /api/lesson-record`, using the canonical calendar+instance reference. The freshly listed reference must exactly match the server's fresh target (title/time/etag and other event identity properties), otherwise record display is stopped. Existing shared eligibility rules exclude all-day, cancelled, declined, transparent, administrative and configured excluded slots from record editing.

The existing attribution policy is retained: `new`, `confirmed`, `legacy_unverified` and `legacy_historical` remain usable; held, changed-title, cross-calendar collision, unavailable and unknown states are blocked. Existing legacy records are not blanket-quarantined or mass-verified. Previous-record snapshots/history returned for the legacy resolution UI are never rendered as current content. Name-correction/inherit/separate decisions and history remain in the old UI; student profile data is not moved or reassigned.

Current record editing covers lesson plan, confirmation test, homework, lesson memo and completion. Saves go to the existing `PUT /api/curriculum/:event_id`, with a frozen complete event reference and the original `record_revision`. Only changed fields are sent, preserving untouched long legacy content. The server retains its fresh event/collision/attribution checks and atomic record CAS. No autosave or write replay is introduced. Inputs/navigation freeze during save. A conflict or uncertain outcome preserves input, disables resend, and offers draft download, read-back, and explicit discard/reload. If the event or attribution changed, read-back hides record content instead of presenting another student's data under the old title. Session loss clears private DOM/drafts and fences late responses.

Related information is read-only: profile memo uses the trimmed event label as its existing name key, matching Tutor without changing the canonical event reference; assigned curriculum names come from student-materials (these IDs are not file-library IDs); a general material-library link and the original Tutor entry remain. Next-lesson preview uses the existing authoritative API, validates the returned source, hides held/unknown plans, and links to a fresh detail read of the target. It does not write to the next event, infer ownership from equal names, or grant permissions. Term lesson counts, curriculum progress, schedule/file attachment management, profile editing and linked next-plan editing remain explicit old-screen operations.

## Authentication and Calendar access

Existing `shared/auth.js?v=12` remains the one auth instance and registered callback. The browser uses its existing Google token helper, like Tutor; no API key, new credential, OAuth scope or callback is introduced. Settings determine selected calendars, deduplicated before reading. Each calendar has independent pagination with JST midnight bounds, 250-item pages and an explicit 20-page/loop error rather than silent truncation. Tokens go only to the fixed encoded Google Calendar endpoint, with redirects rejected. Abort and session-generation checks fence requests and JSON decoding. A failed calendar read produces an explicit retry, not a partial schedule presented as complete. Existing server read APIs may perform their pre-existing baseline observation; no separate baseline initialization/backfill is added or run.

## SS count and original icon set

The SS heading now displays the same `visible.length` used to render cards. Completion filtering, search, sorting and Back/Forward update it together; four completed records show 0 by default and 4 when completion is enabled. No SS data or API behavior changes.

Original Works `index.html` pins Boxicons 2.1.4 and names the existing book-reader/library/calendar-event/note/list-check/git-branch/book-open/briefcase-alt-2 icons. Those exact classes now drive app menus; major edit/save/print/refresh/theme/logout/date/menu controls use the same set. The official pinned npm CSS/fonts are hosted locally with the original MIT license, also emitted as `app/licenses/boxicons.txt`. No React or alternative icon system is added. Permanent labels and aria-hidden decorative glyphs preserve accessible names.

## Validation and publication

All writes are intercepted synthetic API requests; unit tests also cover JST routes, independent Calendar pagination/late responses/loop failures, legacy policy, changed-only patches and preserved source identity. Browser coverage includes current record save, duplicate clicks, unsaved date navigation, 409 and unknown/lost-success outcomes, target changes, holds/collisions/unknown status, recurring composite IDs, duplicate names, profile/material/next read-only boundaries, all-day slots, empty/error recovery, native history, repeated navigation and one auth initialization, 320/390/768/1440 widths, keyboard input, print/PDF, SS count and actual Boxicons font loading. Existing app suites remain required.

Publication requires exact-head app CI and existing Tutor/Worker regression checks. This is frontend/assets only; no manual Worker deploy or production data test write is necessary. The existing automatic Git integration may still rebuild an unchanged Worker on main merge. Rollback of the app commit restores the prior optional entry; original records/APIs remain compatible. Physical iPhone software keyboard/safe-area and authenticated production editing are not established by local browser emulation. Production verification is read-only.
