# D1に保存する生徒・クラス別の授業履歴

このPRは準備用。マージ、本番schema適用、feature切替、実データの取り込みは別途レビューする。本番のCalendar説明は削除しない。元の`curriculum_entries`、帰属履歴、生徒メモ、Google予定は変更しない。

## 保存の単位

`lesson_owners.id`は生徒・集団授業に共通の固定UUID。名前は表示属性であり、別名も同じIDの履歴に残す。同姓同名は別IDを作成できる。既存`students`は本番0件のため、自動で既存生徒IDがあるものとは扱わない。

`lesson_history_records.id`は予定と独立した記録UUID。所有者は作成後に変更するAPIを設けない。4項目、完了、授業日時、当時の予定名、取り込み根拠、revisionを保持する。名前順の一覧は所有者テーブルから、日付順の全履歴は記録テーブルから読む。期間やCalendar予定の存在に依存しない。

`lesson_event_links`は`(calendar_id,event_id)`と記録IDの対応。予定の削除で記録を削除しない。予定の改名・名前の相互入替は表示を保留し、同じ所有者の改名か、別の所有者への変更かを明示確認する。別の所有者への変更は新しい空欄記録を作り、旧記録は旧所有者の履歴に残す。削除された予定からの紐づけ解除もDB内のrevisionで実行できる。再作成した別IDの予定は空欄・未割当となり、保存済み記録を明示的に選んだ場合だけ再接続する。同じ予定ID・名前が再利用されても、created/iCalUID/繰返し元/元日時の生成情報が変化すれば再確認する。名前で記録を検索して所有者を移す処理はない。

次回授業は同じ名前ではなく、確認済みの同じ所有者IDに紐づいた予定から選ぶ。未割当の追加予定は推測で継承しない。次回の読み取りやD1保存でCalendarテンプレートは作らない。生徒メモなど既存の名前キーの機能は今回移動・変更しない。

## 段階と実行条件

`LESSON_HISTORY_MODE`未設定では既存動作を維持する。新しいテーブルを実行時に自動作成しない。

1. 非公開のD1 SQL exportと生Calendarプレビューを取得。対象2件の除外manifestを独立に照合する。
2. `scripts/preview-owner-history.mjs`でローカル復元、新スキーマ追加、再dump・復元、全既存テーブル不変、Calendar最新4項目との差分を検証する。出力には個人情報・DB認証行が含まれるのでPRに添付しない。公開するのは合成データのテスト結果と件数だけ。
3. 別途承認後、`migrations/lesson-owner-history.sql`を本番へ追加適用。除外2件を`lesson_history_exclusions`へ登録し、`lesson_history_policy`にレビュー済みのバックアップSHA256・取得日時・復元検証結果と除外確認を登録する。認証情報やCalendarの説明には触れない。
4. `prepare`で所有者を明示登録し、個別記録の根拠を照合する。既存の名前一致は候補表示にしか使わない。`history.html`の旧記録一覧から現在の予定を探し、内容と取り込み先の固定IDを確認する。現在予定のないもの、所属不明、入替前後が不明なものは保留。名前だけで一括紐づけしない。
5. 別途承認した切替枠で`reconcile`にする。Worksの旧Calendar書き込み・旧DB書き込み・旧履歴undo・空欄テンプレート・旧帰属変更を止め、読み取りを継続する。古いWorkerの処理が残っていないことと、reserved/dispatching/unknownが0件であることを照合する。移行中はGoogle Calendarで授業内容を編集しないよう本人へ説明する。
6. 復元確認済みバックアップが24時間以内の場合のみ、個別の最新プレビュー・所属確認から取り込む。元の121行は更新しない。managed Calendar記録はD1の既存管理履歴を根拠に、最新の4項目を採用する。説明の前後メモも根拠として保存するが4項目へ混ぜない。未管理の4項目や読めない説明は保留する。再取り込みは、D1の取り込み記録が未編集・未再紐づけの場合のみrevisionを照合して更新し、旧値を監査履歴へ保存する。両側の編集があれば自動上書きしない。
7. 全対象をもう一度生Calendarから読み、D1の4項目・帰属・日時と比較する。除外、原121行、生徒メモ、履歴の不変も確認する。未確認分は具体的に列挙し、全件移行と呼ばない。動作確認と取り込み・保留件数をレビューし、`cutover_ready`の根拠を記録する。
8. 別途承認後に`active`へ切り替える。既存授業画面の読み書き、授業予定編集、MCPの予定読み取りはD1固定IDの記録を使う。旧Calendar書き込みは無効になる。旧MCPの予定IDによる更新・一括更新・undoは安全に拒否し、新しい履歴画面へ案内する。新しい履歴APIは既存本人ブラウザセッションだけを許可する。

Calendarは常時ミラーしない。切替後の授業内容はD1が正となる。Calendarに残した説明は今回削除しない。切替後に元の機能フラグを戻すだけではD1での新しい編集が見えなくなるため、切戻しも最新差分・履歴を確認して別途実施する。

## 操作の追跡と競合

所有者・記録・紐づけはrevisionを比較し、D1 batchのCHECK guardで同時更新時は全体をrollbackする。操作UUIDとpayload digestを保存し、同じUUIDの同一要求は保存済み結果を返す。異なる内容での再利用は拒否する。監査はbefore/afterを記録する。

UIは送信前に操作UUIDを記録し、結果不明では入力を保持して後続の保存を停止する。再読み込み後も未確認IDを保持し、操作IDによる読み取り照合から保存済み結果を確認できる。確認できない操作を新しいIDで再送しない。

## 初期データの確認結果（2026-11-01）

原記録121件、students 0件。生Calendarから現在の121予定を確認。既に転記した40件は最新4項目と旧D1の差分0件だった。除外2件を除く119件は、固定IDの所有者をまだ確定していない。40件の予定単位の確認履歴は根拠として使えるが、複数の予定を同じ所有者へまとめる根拠は別途確認する。残る79件は旧記録の所属も含めて確認する。旧名・入替例は同じ名前への自動統合を避ける。

非公開のローカル復元検証では、既存54テーブル不変、新スキーマ追加後64テーブルの再復元一致、integrity_check=ok。これは本番取り込み完了の証拠ではない。

## UI・検証

`tutor/history.html`は通常のHTML/JS。`build-web-ui`に従い既存の固定Bootstrap 6.0.0-alpha.1の隔離済みCSSを再利用し、React・新規CDN・全体CSS変更は追加しない。公式AI索引と導入部品の資料を2026-11-01に参照。ページ遷移は通常のリンクで、アニメーションを保存条件にしない。新しいダイアログやドラッグは導入しない。

`npm test`、`node --test ../tutor/test/*.test.mjs`、`node test/lesson-owner-history.browser.mjs`で保存、競合、入替、削除・再作成、最新値の取り込み、失敗・不明時の再送停止を検証する。ブラウザ確認はChromiumのPC/390px幅・reduced motion。iPhone Safariの実機操作は未確認。
