# Works unified shell: ToDo, Memo and Wiki

The optional `/app/` entry adds existing-item lists, details and editing for ToDo, Memo and Wiki. The existing top page, URLs, authentication, API contracts and databases remain in place. React and additional dependencies are not introduced.

The operations category opens ToDo and Memo internally; the workflow category opens Wiki internally. Each module links to its original screen for creation and advanced operations. ToDo supports name, memo, status and progress; Memo supports title and every existing body/supplement; Wiki supports title and Markdown source. Category/tag management, cloning/checklists/roles, Wiki folders, sources, proposals, confirmation and restoration remain in the original screens. Wiki text is rendered as escaped text, not HTML or executable Markdown. Existing confirmation status is preserved; there is no new confirmation or execution operation.

One Framework7 view owns URL history (`/app/#!/todo/:id/`, `memo`, `wiki`). List search and Wiki pagination survive module navigation in memory and reset on sign-out. Direct links and reload fetch current state. Mounted modules own abortable event/request lifetimes and clear their DOM on unmount. Existing session initialization is shared once. Sign-out/session expiration clears module state and retained private DOM.

ToDo/Memo send a full preserved snapshot with its original revision to their existing PUT APIs. Untouched tasks, roles, checklist data, operation receipts, categories, tags and memo parts are preserved. Wiki POSTs its existing page revision and preserved content fields to the existing save endpoint. Backend revision checking remains the concurrency boundary. No schema or migration is needed.

While saving, form fields and cancel are disabled, navigation is held, and repeated submission is ignored. No automatic mutation retries occur. A 409 or unconfirmed response keeps the input, disables another submission and offers a read of the latest saved record, a JSON download of the input, and explicit discard/reload. Matching read-back is described as matching content, not proof of which client wrote it. It never rebases or overwrites a newer revision automatically. The same protection applies after a server commits but its success response is lost. Downloads contain private draft content and are initiated only by the user.

Validation uses intercepted synthetic browser sessions and API responses only: list/detail/edit, complete snapshot preservation, single-flight saves, conflicts, lost-success reconciliation, unsaved navigation, Back/Forward, direct links/reload, repeated mounts, keyboard navigation, mobile/desktop widths, and existing SS/auth regressions. A real signed-in iPhone/Mac session is a separate remaining acceptance check; local browser emulation does not establish it.

Publication is a frontend-only change: build and commit `app/` together with `prototype/` sources, require the exact-head app-shell CI (including reproducible assets and browser tests), then merge through the existing Pages workflow. Do not run a separate manual Worker deployment. Rollback the frontend commit/build to restore the previous optional entry. Saved content uses existing APIs and remains readable by original pages; there is no data rollback or attribution change.
